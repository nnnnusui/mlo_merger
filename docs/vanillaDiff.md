# Vanilla YMAP バージョン差分

vanilla-cache が生成する「vanilla YMAP のバージョン間差分」の仕組みと、実データでの検証結果、残っている課題をまとめる。

> **現在、差分の生成は無効化している。** vanilla バージョンの推定は見送りとし（理由は [reference.md の「Limitations」](reference.md#limitations) を参照）、`BuildVanillaCache::run_cache` での生成呼び出しと、freshness check での確認をコメントアウトしている。生成コードと読み出し API は残している。

計測は 2026-10-27、`asset/vanilla`（0000-base 〜 0102-patch2026_01）に対して行った。

## 目的

- 各 vanilla YMAP について、最古のファイルに差分を順に適用すれば、任意のバージョンを完全に復元できるようにする。
- source YMAP がどの vanilla バージョンを元に作られたかを推定（差分が最小になるバージョンを探索）する際の土台にする。

## 出力

| パス | 内容 |
|---|---|
| `vanilla-cache/ymap_versions.json` (`VanillaYmapVersionIndex`) | 2 つ以上のバージョンを持つ YMAP ごとに、内容を持つバージョンを古い順に列挙 |
| `vanilla-cache/diff/{version}/ymap/{name}.diff.json` (`VanillaYmapDiff`) | そのバージョンでの内容と、直前に内容を持っていたバージョンとの差分 |

- 差分の基準は「過去ファイルが存在するバージョンのうち最も新しいもの」。たとえば 0000-base → 0014 → 0072 と変化した YMAP では、0072 の差分は 0014 からの差分になる。
- 途中のバージョンで初めて追加された YMAP（6061 件）には差分がない。追加されたファイル自体が差分適用の起点になる。
- 読み出しと復元は `vanilla_cache::ymap_history(cache_dir, name)` と `VanillaYmapHistory::rebuild(vanilla_dir, index, hash_names)` で行う。
- 前回の差分は、両ファイル・差分レイアウト・アルゴリズムバージョン・`hash_names.json` が変わらない限り再利用する。`--force` 指定時はすべて取り直す。
- 差分は compact JSON で書く。合計は約 340 MB、生成時間は release ビルドで約 25 秒。

## 差分の取り方（exact モード）

source 差分（merge 用）とは別に、復元のための設定で差分を取る。

- 値の許容値をゼロにする（`MatchTolerances::ymap_exact()`）。項目の対応付け（pairing）の許容値は既定値のまま。
- エンティティの親は生の `parentIndex` として記録する（`raw_entity_parents`）。通常の `apply` も、生の index で表された親の変更を書き戻す。
- 生成時に差分を実際に適用して検証し、一致しなければ警告を出す。

merge で無視していた変更（name・flags・extents・block・distant LOD light counts・physics dictionary の削除）は、差分には常に記録する。無視するかどうかは merge 側の条件（`IgnoredChange::MERGE`）で決め、リソースの差分にだけ適用する（vanilla overwrite の差分には適用しない）。

## 検証結果

- 1937 件のバージョン遷移すべてで、最古ファイルからの連鎖適用によって各バージョンを完全に復元できた（ignored テスト `ymap_version_diffs_rebuild_every_vanilla_version`）。
- ただし、後述の並べ替えに対しては現状「削除＋再追加」「丸ごと置換」「配列の全書き換え」という回避策で対処しており、差分が大きく、何が変わったかも読み取りにくい。

### 最初の実験で復元できなかったもの

許容値ゼロでも、当初は 56 件が復元できなかった。

| 原因 | 件数 | 内容 |
|---|---|---|
| grass | 50 | bounds 変更時の再パック誤差と、バッチ・インスタンスの並べ替え |
| エンティティの並べ替え | 4 | 残る項目の順序が記録されない |
| physics dictionary | 2 | 削除が記録されない（merge 向けの仕様が差分自体に入っていた） |

エンティティの並べ替えを記録しないと、後続バージョンの差分の index がずれ、連鎖的にファイルが壊れる（例: `hw1_01_strm_0.ymap` は 0015 の並べ替えが失われ、0072 で破損した）。

## 並べ替えの計測

pairing を取ったうえで、新しい側の index の最長増加部分列を求めると、移動した項目の最小集合が正確に分かる。配列ごとの結果は次のとおり。

| 配列 | 並べ替えがあった数 | 移動した項目数 |
|---|---|---|
| エンティティ | 4 ファイル | 6 |
| grass バッチ | 50 ファイル中 46 | 1,202 |
| grass インスタンス（バッチ内） | 4,882 バッチ | 約 173 万 |
| occlude model の三角形 | 変更された 401 モデルすべて | 38,452 |
| box occluder、LOD light、distant LOD light、car generator、time cycle modifier、physics dictionary、prop instance | 0 | 0 |

### エンティティ

GUID による対応付けは問題なく機能している。並べ替えが起きた 4 件はいずれも全エンティティが対応し、重複 GUID もない。順序だけが変わっている。

| ファイル | エンティティ数 | 移動 |
|---|---|---|
| hw1_01_strm_0（0015） | 334 | 2（例: #330 が #216 の前へ） |
| hw1_01_strm_1（0015） | 328 | 2（隣接入れ替え） |
| sc1_13_strm_0（0015） | 362 | 1 |
| ss1_13_strm_0（0014） | 460 | 1（#11 と #12 の入れ替え） |

原因は対応付けではなく、差分の適用が「対応した項目を vanilla 側の順序に戻す」ことにある。差分は `after_index` をすでに記録しているが、適用時には使われていない。

### grass の再パック誤差

0014 で変更された grass バッチの約 250 万インスタンスを、インスタンス同士を対応付けたうえで比較した。

- 軸ごとに **92.5% が完全一致、7.5% が ±1 パック単位**。それ以上の誤差はない。
- ワールド座標での誤差は最大 **3.9 mm**。これはちょうど 1 単位（bounds の大きさ / 65536）に当たる。

再パック誤差は量子化 1 単位分の丸め誤差に過ぎない。ただし主因は並べ替えのほうにある。0014 で変更された 4,897 バッチのうち、bounds が変わらない 855 バッチも並べ替えだけが原因で復元できなかった。

### occlude model の三角形

ゲーム側は occlude model を変更するたびに三角形の順序も入れ替えている。現状は exact モードで occlude model を対応付けないことで回避しているが、その結果、変更されたモデルはすべて丸ごと置換として記録される。

## 現状の回避策

| 対象 | 回避策 | 欠点 |
|---|---|---|
| エンティティの並べ替え | 移動分を「削除＋再追加」として記録（最長増加部分列で最小化） | エンティティ全体を複製する |
| grass | 正確に復元できないバッチを丸ごと置換 | 差分が大きい（0014 の grass が全体の大半） |
| occlude model | 対応付けず、変更されたモデルを丸ごと置換 | 三角形の変更が読み取れない |
| その他の配列 | 適用して一致しなければ「全削除＋全追加」に書き換え | 今回の実データでは grass 6 ファイルのみ該当 |

## 改善案

1. **struct-diff の配列差分に移動の記録を追加する**（例: `Moved { index, after }`）。
   - exact モードのときだけ、上記の最小移動検出で記録する。
   - エンティティ、occlude model の三角形、grass バッチ、grass インスタンスをすべて同じ仕組みで扱える。
   - merge では移動を無視する（merge 専用の条件の一つにする）。
   - occlude model を exact モードでも対応付けられるようになる。
2. **exact モードでは、grass インスタンスのパック済み座標が異なる場合にそれを記録する。** 実際には ±1 ずれる 7.5% の値だけが対象になる。
3. 「配列の全書き換え」は安全網としてだけ残す。

0014 の grass のようにほとんどのインスタンスが並べ替わっている場合は、移動を 1 件ずつ記録するより丸ごと置換のほうが小さくなりうる。差分を小さく保つには、バッチごとに両者の大きさを比べて小さいほうを選ぶ。

## 今後の利用: source のベースライン推定と合成

想定している流れは次のとおり。

1. source YMAP と各 vanilla バージョンを比較し、差分が最小のバージョン B を推定する。
2. source の差分を B に対して取る。source が B から書き写しただけの値は差分に現れなくなる。
3. 合成時、B から最新版への vanilla 差分と source 差分を合わせて、最新の vanilla に適用する。

3 の「差分同士の合成」は、source 差分を最新版へ付け替える（rebase する）処理と見なせる。source 差分の index は B の配列を指しているので、B から最新版への項目の対応表（index の写像）があれば付け替えられる。

- 対応表は vanilla 差分の連鎖から作れる。移動が正確に記録されていれば、対応表も正確になる。
- 生アーカイブ（`asset/vanilla`）には全バージョンのファイルが残っているので、B と最新版を直接対応付けて対応表を作ることもできる。
- B から最新版の間で vanilla 側が削除・変更した項目を source も変更している場合は競合になる。報告の仕方と優先順位を決める必要がある。
- LOD light ペア（並行配列）、エンティティの親参照（他 YMAP をまたぐもの）、diff ドキュメントへのベースバージョンの記録も、あわせて対応が必要になる。
